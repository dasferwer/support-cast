# Запуск и работа с API

`make up` собирает runtime, поднимает PostgreSQL, выполняет Alembic и идемпотентный seed, затем запускает API и worker. Порт 8170 доступен только через loopback; база наружу не опубликована. Пароль demo и JWT-секрет предназначены для локальной демонстрации. Свой секрет можно задать через `.env` по примеру `.env.example`.

## Загрузка ряда

1. `POST /auth/register` с `email` и `password`, затем `POST /auth/login`. В остальных запросах передавать `Authorization: Bearer <access_token>`.
2. `POST /series` с `{"name":"Support queue"}`. Прочитать созданный ряд через `GET /series/{id}` и сохранить заголовок `ETag` целиком, с кавычками.
3. `PUT /series/{id}/observations` с `If-Match`, новым `Idempotency-Key` и телом `{"observations":[{"day":"2025-01-01","count":42}, ...]}`. Многоточие означает другие дни, а не часть JSON; полный рабочий пример находится в `scripts/smoke.py`.
4. Опросить `GET /jobs/{job_id}` до `ready` или `failed`. Последняя версия доступна через `GET /series/{id}/forecast`.
5. Для сценария численности вызвать `/jobs/{job_id}/staffing?handling_minutes=8&productive_hours=6`.

Загрузка принимает до 3650 дат, от 0 до 1 000 000 обращений за день либо `null`. Для расчёта нужен календарный диапазон от 56 до 3650 дней, минимум 28 известных значений и 14 известных за последние 28 дней. Даты должны относиться к завершённым дням по часам сервера; в Docker используется UTC. У пользователя может быть до 20 рядов. Начало прогноза — день после последней даты ряда, а не после текущей даты сервера. Исторические данные в demo поэтому дают исторический прогноз.

## Если что-то остановилось

```bash
docker compose ps
docker compose logs --tail=100 api worker
docker compose exec -T api python scripts/seed.py
uv run python scripts/recovery_smoke.py
```

У worker есть heartbeat и Docker healthcheck. После SIGKILL дождаться истечения lease: тот же job должен перейти из `running` в `ready` с увеличенным числом попыток. При `failed` прочитать `error`, проверить наличие правильной модели и загрузить исправления новой ревизией. Автоматический retry ограничен тремя попытками.

`WORKER_DELAY_SECONDS` нужен только для воспроизведения падения в recovery-скрипте. В обычном запуске он равен нулю. Скрипт восстанавливает обычный worker в `finally`.

`/health` проверяет базу; `/metrics` содержит HTTP-метрики. Логи включают идентификатор запроса и время ответа, без тела обращения. Удаление старых рядов, хранение архивов, rate limit регистрации и резервное копирование за пределами локального Compose пока не реализованы.

Тесты запускаются в отдельной временной базе `supportcast_test`. После проверки её можно остановить: `docker compose --profile test stop test-db`. Не использовать `down -v`, если нужна сохранённая история.
