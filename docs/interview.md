# Как объяснить проект на интервью

Я сделал сервис дневного прогноза нагрузки с версионированием истории. Клиент загружает наблюдения, а API одной транзакцией сохраняет данные и задание. У задания собственная копия истории и хеш модели, поэтому можно объяснить, откуда взялся результат. При падении worker повторяет расчёт; старое поколение исполнителя уже не может записать результат.

Для модели я сравнил недельный повтор с Ridge на последовательных временных отрезках. Пропуски заполняются только из прошлого, параметры выбираются до теста. В runtime оставлены NumPy и числовой JSON, обучение отделено от API.

Слабое место демонстрации — данные. Обращения после Sandy не отражают обычную службу поддержки, а в конце ряда они очень редкие. Я сохранил абсолютные и относительные ошибки, включая неудобные результаты. Улучшение над baseline здесь подтверждает конкретный эксперимент, но не готовность модели управлять реальными сменами.

На показе: запустить `make smoke`, затем `make recovery`, открыть отчёт модели и объяснить разницу между повтором вычисления и единственным принятым результатом. Следующим шагом для реальной команды были бы её история обращений, календарь и SLA, затем новая оценка и наблюдение за ошибками.
